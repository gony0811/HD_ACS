## A. 응답 스키마와 에러코드 — 최우선

**A-1. 에러코드 전체 목록**
로봇 에러 코드(Modbus Input 11 및 `GET /robot/status`의 `error` 필드)의 **전체 값과 의미**를 표로 요청드립니다.
관제는 각 코드를 **주행 실패 / 측위 상실 / 장비 이상 / 정지 중** 4개 분류로 매핑해야 하며, 이 분류가 재시도·스킵·알람 정책을 그대로 결정합니다. 현재 이 표가 없어 장애 처리 로직을 확정하지 못하고 있습니다.

**A-2. `GET /api/v3/robot/status` 응답 필드**
- 전체 필드 목록과 각 의미
- `schedule`의 **값 목록** — 특히 "이동 중 / 도착 완료 / 큐 비어 있음"을 어떻게 구분합니까?
- `error`의 형태(단일 코드인지 배열인지), 그리고 **오류 해소 시 자동으로 비워지는지**

**A-3. `GET /api/v3/robot/pose` 응답 필드**
- 좌표·라이다·**맵 일치율** 각각의 필드명과 단위
- 맵 일치율의 **정상 주행 시 통상 범위**와, **"측위를 신뢰해도 된다"고 판단할 임계값 권고치**
  (값을 읽을 수 있다는 것은 확인했습니다. 저희에게 없는 것은 판정 기준입니다.)

**A-4. 실패 응답 `code` 체계**
성공 `{code:0}` 외 실패 `code`의 값·의미, 그리고 이것이 A-1의 로봇 에러코드와 **같은 체계인지 별개의 API 레벨 코드인지**.

**A-5. 문서 형태의 응답 사양**
Swagger 정의에 응답 스키마가 비어 있는데, **응답 필드를 정리한 문서나 예시 응답 모음**이 따로 있다면 제공 부탁드립니다.

## B. 층 전환 — 재측위와 유사 형상 구역

배경: 화물창 4개 층을 통합맵에 타일 배치하고, 층 이동 후 재측위로 층을 확정하는 게이트를 설계 중입니다.
`POST /api/v3/robot/pose`(위치 보정)와 `GET /api/v3/robot/pose`(맵 일치율)로 **REST만으로 구현 가능**하다고 이해했습니다. 맞는지 포함해 확인 부탁드립니다.

**B-1. `POST /robot/pose`의 동작과 `tuneFlag`**
- 이 호출은 **지정 좌표 주변을 탐색해 재측위**하는 것입니까, 아니면 **주어진 좌표를 그대로 현재 위치로 설정**하는 것입니까?
- `tuneFlag: true/false` 각각의 동작 차이는 무엇입니까?
- 탐색을 한다면 **탐색 반경**은 얼마이며 조정 가능합니까?
- **완료·실패 판정 방법**과 통상 소요 시간·타임아웃 상한을 알려주십시오. (응답이 즉시 돌아온다면 완료를 어떻게 확인합니까?)

**B-2. Modbus PoseSearch(Holding 20~26)와의 관계**
`POST /robot/pose`와 Modbus PoseSearch는 **같은 기능입니까, 다른 기능입니까?** 권장 경로는 어느 쪽입니까?

**B-3. 유사 형상 구역 오수렴 (1차 4.3 미회신)**
통합맵에 **형상이 매우 유사한 층 타일 4개**가 들어갑니다.
- 재측위가 **다른 층 타일로 잘못 수렴**할 가능성이 있습니까?
- 있다면 방지 방법(초기 추정 좌표 강제, 탐색 범위 제한, 구역 지정 등)이 있습니까?
- 오수렴이 발생했을 때 **외부에서 검출 가능한 지표**가 맵 일치율 외에 있습니까?

> 배경: 층을 오인한 채 주행하면 로봇은 정상 동작하지만 **검사 위치만 틀리는** 형태가 되어 사후 검출이 어렵습니다. 이 경로를 차단하는 것이 이번 연동의 안전 요건입니다.

## C. 목적지 큐와 정지 제어

1차 회신에서 `/robot/go`가 **큐에 추가(append)**되며, 교체하려면 `POST /robot/state`가 필요하다고 확인했습니다. 실물 스펙에서 관련 엔드포인트가 여럿 확인되어 관계 정리가 필요합니다.

**C-1. `POST /robot/state`의 `state` 값 목록**
예시가 `"stop"` 하나뿐입니다. 가능한 값 전체와 각 동작(시작/정지/일시정지/재개 등)을 알려주십시오.
- **정지 시 큐에 남은 목적지는 유지됩니까, 삭제됩니까?**
- 정지 후 **재개**가 가능합니까, `/go` 재발행만 가능합니까?
- 정지 완료(감속 완료) 시점은 어떻게 확인합니까?

**C-2. `/robot/go` · `/robot/job/add` · `/robot/task` · `/robot/task/clear`의 관계**
- 1차 회신에서 말씀하신 "큐"는 이 중 어느 것입니까?
- `/robot/task/clear`는 **`/go`로 쌓인 목적지도 함께 비웁니까?**
- 목적지를 완전히 교체하는 **권장 호출 순서**를 알려주십시오. (관제는 한 번에 한 정차점만 발행하고, 교체 전 큐가 비었음을 확인하려 합니다.)

**C-3. 큐 조회·길이**
현재 큐에 등록된 목적지 목록 또는 남은 개수를 조회할 방법이 있습니까? 큐 최대 길이와 초과 시 동작은 어떻게 됩니까?

**C-4. 도착 판정 시점과 정밀도**
- `stopFlag=true` 정차 시, **각도 보정 완료까지 끝난 시점**이 `schedule`상 "도착"으로 반영됩니까, 위치 도달 시점입니까? (정차 직후 협동로봇 동작을 시작하므로 보정 완료 시점 판정이 필요합니다.)
- `stopFlag=true` 기준 통상 정차 오차(위치 m / 각도 rad) 실측 범위를 알려주십시오. 관제 허용오차를 잠정 0.08 m / 0.07 rad 로 두었습니다.

**C-5. 비상정지와의 관계**
관제의 기능 정지(주행 정지 + 코봇 정지)에 `POST /robot/state` 정지를 쓰려 합니다.
- 이 정지가 **하드웨어 비상정지(안전 회로)와 별개**인 소프트 정지가 맞습니까?
- 정지 상태에서 `/go`를 발행하면 거부됩니까, 큐에만 쌓입니까?

## D. 맵 운용 — 통합맵 vs 층별 맵 전환

`GET /map`, `GET /map/info`, `POST /map/load`가 있어 **층별 맵을 두고 전환하는 방식도 가능**해 보입니다. 1차에서 권해주신 통합맵과 비교해 선택하려 합니다.

**D-1. 두 방식의 권장 비교**
① 층별 맵 4장 + `/map/load` 전환 ② 통합맵 1장 + 타일 배치 — **현장에서 어느 쪽을 권하십니까?** 판단 근거도 함께 부탁드립니다.

**D-2. `/map/load` 소요와 후속 절차**
- 맵 로드에 걸리는 **통상 시간**은 얼마입니까?
- 로드 직후 **재측위가 반드시 필요합니까?** 이전 좌표는 유지됩니까?
- 로드 완료를 외부에서 확인하는 방법이 있습니까?

**D-3. `GET /map/info` 응답 필드**
현재 로드된 맵의 **식별자/버전/해상도/원점** 등 어떤 필드가 나옵니까?
(관제가 도면↔맵 변환 파라미터를 맵 버전에 묶어 관리하므로, 맵이 바뀐 것을 모른 채 옛 좌표를 발행하는 사고를 막는 데 필요합니다.)

**D-4. 타일 배치 제약**
통합맵을 쓸 경우 층 타일 간 **최소 이격 거리** 권고치가 있습니까? 미지 영역으로 분리하면 되는지, 벽으로 막아야 하는지.

**D-5. 거점 좌표의 기준**
`POST /plan/waypoint`로 좌표를 직접 등록할 수 있음을 확인했습니다. 이때 `pose`의 x/y/rz는 **현재 로드된 맵의 좌표계(원점=좌측 하단, rz=X축 CCW)** 기준이 맞습니까?
또한 일부 층만 재스캔해 통합맵을 갱신할 경우 **기존 거점 좌표가 유지**됩니까?

## E. 운영 파라미터

**E-1. 폴링 주기** — `GET /robot/status`·`/robot/pose`의 **권장 폴링 주기**와 rate limit이 있습니까? 관제는 2초 주기 상태 보고 + 이벤트 시 즉시 보고 모델이라 200~500 ms 폴링을 검토 중입니다.

**E-2. Modbus와 REST의 권장 사용 구분**
`POST /robot/modbus`로 홀딩 레지스터를 REST에서 직접 쓸 수 있음을 확인했습니다.
- Modbus TCP 직접 연결 대신 **이 경로로 통일해도 되는지** 권장 의견을 부탁드립니다.
- 두 경로를 동시에 사용할 때 우선순위나 주의점이 있습니까?
- `GET /robot/brief`가 반환하는 Modbus 정보의 범위(어느 레지스터까지)를 알려주십시오.

**E-3. WorkStatus(Input 64)** 가 REST `/go` 이동 시에도 동일하게 반영됩니까? `status.schedule`과 WorkStatus 중 어느 쪽을 정본으로 보아야 합니까?

**E-4. Wi-Fi 로밍** 시 TCP(Modbus)/HTTP(REST) 세션 유지 특성과 두절 시 권고 재접속 방식(타임아웃·재시도 간격).

**E-5. `/api/v3/proxy`** 의 용도와 사용 시 주의점을 알려주십시오. (유선/무선 네트워크 간 REST 프록시로 이해했습니다.)
