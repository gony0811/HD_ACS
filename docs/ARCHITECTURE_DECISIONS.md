## ADR-001. 로봇 통신 인터페이스 및 실행 모델 ✅

**질문**: HD_ACS와 로봇(AMR/협동로봇/검사장비)은 어떤 프로토콜로 통신하는가? 검사 실행 로직은 어디서 도는가?

**결정** (2026-07-15):
- HD_ACS ↔ HD_AMR 통신은 **VDA 5050** 을 채택한다.
- 로봇 측에는 AMR·협동로봇·검사장비를 **모두 통합 제어하는 HD_AMR S/W가 존재**한다. HD_ACS는 개별 장치와 직접 통신하지 않으며, **유일한 상대는 HD_AMR, 유일한 인터페이스는 VDA 5050** 이다.
- **검사 시퀀스와 자세 제어는 전부 HD_AMR의 책임**이다. HD_ACS는 "어느 지점에서 어떤 검사 작업을" 수준(Order의 노드 + 액션)까지만 정의하고, "어떻게"(협동로봇 웨이포인트, 장비 세부 제어)는 알지 못한다.
- 실행 모델은 **온보드 실행형**: HD_ACS가 Order를 전달하면 HD_AMR이 이동·검사를 자율 실행한다.

**결과 (Consequences)**:
- 관제 코어에 **VDA 5050 마스터 어댑터**와 **MQTT 브로커**가 필수 구성요소가 된다.
- 협동로봇 검사 동작, 촬영 트리거 등 표준에 없는 동작은 **커스텀 액션(action)** 으로 정의한다 → 액션 카탈로그 필요 (ADR-008)
- 표준 프로토콜 채택으로 추후 이기종 로봇 추가에도 유리하다.

## ADR-002. 네트워크 및 통신 두절 대응 ✅

**질문**: 화물창 내 네트워크 환경은? 통신 두절 시 로봇은 검사를 계속해야 하는가?

**결정** (2026-07-15):
- LNG 화물창 내부는 **무선 Wi-Fi** 로 구성한다.
- **통신 두절 시에도 로봇은 검사를 계속 수행**해야 하며, **재접속 시 동기화**가 이루어져야 한다.

**결과**:
- 스텝 단위 원격 지시는 불가 → **시나리오 전체(또는 큰 구간)를 Base로 선(先)릴리즈**하여 오프라인 진행을 보장한다 (VDA 5050 Base/Horizon 모델 활용).
- 연결 상태는 VDA 5050 `connection` 토픽(MQTT Last Will)으로 감지한다.
- 재접속 시 로봇의 `state`(lastNodeId, actionStates)를 기준으로 **로봇 상태 우선(robot-is-truth)** 동기화를 수행한다.
- 두절 구간의 검사 수행 이력(타임스탬프 포함) 재전송은 VDA 5050 표준 범위 밖 → 확장 설계 필요 (ADR-008)

## ADR-003. 배포 토폴로지 및 운영 규모 ✅

**질문**: 관제 서버는 어디에 두는가? 로봇 대수와 동시 사용자 수는?

**결정** (2026-07-15):
- 관제 서버는 **현장 이동식**, **폐쇄망** 운영 (클라우드 없음).
- 로봇 **1대로 시작**, **추후 다수 로봇 동시 운영** 가능성을 열어둔다.
- **여러 사용자가 동시에 모니터링** 할 수 있어야 한다.

**결과**:
- 모든 구성요소(브로커, API 서버, DB, 웹 대시보드)를 이동식 서버 1대에 배치 가능하게 설계하고, 외부 인터넷 의존(패키지 다운로드, 라이선스 인증, 지도 타일 등)을 제거한다.
- 코어 데이터 모델은 처음부터 `robotId` 를 키에 포함하여 fleet 확장 시 구조 변경이 없게 한다. 단, 다중 로봇 교통 관리(경로 충돌 회피)는 초기 범위에서 제외한다.
- 다중 사용자 실시간 모니터링 → 서버 푸시 계층 필요 (ADR-005의 SignalR)

## ADR-004. 검사 데이터 처리 범위 ✅

**질문**: 검사 이미지/판정 데이터는 누가 관리하는가?

**결정** (2026-07-15):
- **검사 S/W는 별도로 존재**한다. HD_ACS는 이미지·측정 원본을 다루지 않는다.
- HD_ACS는 **촬영 명령 전송 시 현재 위치를 전달**하고, 응답으로 **촬영 성공/실패**를 수신·기록한다.

**결과**:
- HD_ACS 데이터 모델은 **검사 수행 이력(위치, 시각, 성공/실패, 시도 횟수)** 중심으로 단순화된다. 이미지 스토리지/파이프라인 설계 부담이 없다.
- 촬영 명령은 VDA 5050 커스텀 액션으로 정의하고 위치를 액션 파라미터로 전달한다.
- 검사 S/W의 판정 결과와 ACS 수행 이력의 사후 대조를 위해 **위치+시각 키 정합성**(좌표계·타임스탬프 규약 공유)이 중요하다 (⬜ Q2).

## ADR-005. UI 아키텍처 ✅

**질문**: 운영자 UI는 어떤 형태인가?

**결정** (2026-07-15):
- 주 운영 화면은 **3D 뷰 + 전개도** 가 필요하므로 **데스크톱 앱(WPF)** 으로 개발한다.
- 서버는 **REST API** 를 제공하여 **Web 대시보드, 태블릿** 등 다양한 클라이언트를 붙일 수 있게 한다.
- (2026-07-15 재확정) NAMUGA_ACS의 Avalonia UI 자산과의 충돌 검토(Q5′) 결과, **3D 뷰 요구를 우선하여 WPF로 확정**한다. Avalonia UI 자산은 ViewModel/Service 패턴 수준에서만 이식한다.

**결과**:
- **API-First**: 시나리오 CRUD, 미션 제어, 상태 조회 등 모든 기능을 REST API로 노출하고 WPF도 이 API만 사용한다 (UI의 서버 내부 직접 접근 금지).
- 실시간 상태 전파는 폴링이 아닌 **SignalR(WebSocket)** 허브로 다중 클라이언트에 푸시한다.
- 3D/전개도 렌더링은 WPF 클라이언트 책임 (라이브러리 후보: HelixToolkit 등 — ⬜ Q5).

**개정** (2026-09-03, macOS 운영 요구):
- 주 운영 UI를 **Avalonia 11 크로스플랫폼 데스크톱 앱(Win/macOS/Linux)** 으로 이행한다. 검토·대안 비교·이행 단계는 `docs/UI_CROSS_PLATFORM_REVIEW.md`.
- 구조: 프레임워크 중립 공용 코어 `HD.Acs.UI.Core`(Models·REST/SignalR 서비스·ViewModels, net8.0) + 헤드 2종 — `HD.Acs.UI`(WPF, 기존)와 `HD.Acs.UI.Desktop`(Avalonia, 신규). 두 헤드는 같은 VM을 바인딩하며 UI 스레드·대화상자는 `IUiDispatcher`/`IDialogService`/`IProjectDialogService` 추상화로 주입한다.
- 컨트롤: Telerik(Avalonia 라인 없음)은 Avalonia 내장 컨트롤(DataGrid·NumericUpDown·TabControl 등)로 대체. 3D 뷰는 HelixToolkit 등가물이 없어 **코어의 순수 카메라·투영·깊이 정렬 + 2D DrawingContext 소프트웨어 투영 렌더러**로 구현한다(Phase 3, 씬 규모가 수십 도형이라 충분).
- WPF 헤드는 Avalonia 헤드가 기능 동등성(3D 포함)에 도달할 때까지 유지하고, 이후 은퇴 여부를 결정한다(Telerik 라이선스·이중 유지보수 제거).
- API-First·SignalR 푸시 원칙은 불변(두 헤드 모두 동일 계약만 사용).

## ADR-007. 비상정지 및 원격 조작 ✅

**질문**: 관제에서 비상정지가 가능해야 하는가? 원격 수동조작(teleop)이 필요한가?

**결정** (2026-07-15):
- 관제 시스템에서 **비상정지를 실행할 수 있어야 한다**.
- **원격 수동조작(teleop)은 불필요**하다.

**결과**:
- 비상정지는 VDA 5050 **instantActions** (즉시 액션)로 전달한다.
- ⚠️ **주의**: Wi-Fi/MQTT 경유 정지는 **기능적 정지(functional stop)** 이며 안전 규격(safety-rated) 정지가 아니다. 통신 두절 시 동작하지 않으므로, 인명 안전용 비상정지 체계(하드웨어 E-Stop, 안전 센서)는 로봇 측에 독립적으로 존재해야 하며 관제 정지는 이를 보조하는 운영 수단으로 정의한다 (⬜ Q7).
- teleop 제외로 저지연 영상 스트리밍/조작 계층이 불필요 → 아키텍처 단순화.

## ADR-008. VDA 5050 프로파일 정의 🔶 → 사양서로 이관

**질문**: VDA 5050을 본 프로젝트에 어떻게 구체화(프로파일링)하는가?

**결정** (2026-08-27): 프로파일 상세는 **`docs/VDA5050_INTERFACE_SPEC.md`** (HD_ACS ↔ HD_AMR 인터페이스 사양서)로 단일화한다. 본 ADR은 결정 요지만 유지하며, 사양서와 다르면 사양서가 우선한다.

**확정 세부**:
- ✅ **버전 = VDA 5050 2.0** (헤더 `2.0.0`, 토픽 `uagv/v2` — 구현 기준 확정)
- ✅ 커스텀 액션 카탈로그: `startWeldInspection`(NODE/HARD, param_schema 시드) + instantActions `initPosition`/`emergencyStop` — 사양서 §5/§8
- ✅ 맵/좌표계 규약: 층=맵(`{tank}-L{n}`), VDA 구간 m/rad, 도면→맵 T_W_D 변환 — 사양서 부록 B
- ✅ 두절 구간 이력: 최신 state 스냅샷 동기화로 충분(소급 재전송 없음)을 기본 계약으로 — 상세 이력 확장은 사양서 §10 N8 협의
- ✅ MQTT: Mosquitto(:1883, 폐쇄망 평문), 전 채널 QoS 1, connection만 retain+Last Will — 보안(TLS) 여부는 사양서 §10 N9 협의

**잔여 미결**: HD_AMR 측 회신 대기 항목은 사양서 §10 협의 표(N1~N11)에서 관리한다.

## ADR-009. 참조 아키텍처 — NAMUGA_ACS 플랫폼 기반 개발 ✅

**결정** (2026-07-15):
- 사내 운영 중인 **NAMUGA_ACS**(.NET 8 AMR 관제 플랫폼)를 참조 아키텍처로 채택하고, 그 계층 구조와 코어 자산 위에서 HD_ACS를 개발한다.

## ADR-010. 미션 오케스트레이터 구현 방식 ✅

**질문**: 미션 오케스트레이터를 무엇으로 구현하는가? (구 Q8)

**배경**:
- NAMUGA_ACS는 Elsa 3.5 워크플로우로 오케스트레이션했으나, Studio 시각 편집을 실제로 활용하지 못했고 S/W 수정에 한계를 경험했다.
- HD_ACS는 온보드 실행형 + Base 선릴리즈 + robot-is-truth 구조라 관제 오케스트레이터의 본질이 "이벤트 구동 상태 추적기 + 정책 엔진"으로 단순화된다. 워크플로우 엔진의 내구 실행이 필요한 이유(장주기 스텝 구동, 크래시 복구)의 대부분이 아키텍처 차원에서 해소된다.

**검토 대안**:
| 안 | 내용 | 평가 |
|---|---|---|
| 1안 | **Stateless 라이브러리 상태머신** + EF Core 상태/이벤트 로그 | ✅ 권장 — 경량, C# 디버깅, DOT 그래프 자동 export로 상태도 시각화(편집은 코드·확인은 그림), robot-is-truth로 복구 단순, 정책은 시나리오 데이터 파라미터화 |
| 2안 | 순수 자체 구현 (enum + 전이 테이블) | 의존성 0이나 Stateless 기능(가드/액션/그래프)의 재발명이 됨 |
| 3안 | DTFx / Temporal 내구 실행 엔진 | 폐쇄망·현장 유지보수와 상충(Temporal 서버 필요), 규모 대비 과함 |
| 4안 | Elsa code-first 한정 (Studio 배제) | 기존 경험 활용 가능하나 수정 한계의 원인(추상화 계층·버전 변동)이 남음 |

**결정** (2026-07-15): **1안 확정** — Stateless 라이브러리 기반 명시적 상태머신 + EF Core 상태/전이 이벤트 로그. 상태도는 DOT export로 자동 생성하여 문서·UI에 제공한다. 재시도/스킵 정책은 시나리오 데이터 파라미터로 외부화한다.

## ADR-011. 프로세스 구조 — 단일 프로세스 모놀리스, 이중화 미도입 ✅

**질문**: 실행 프로세스를 하나로 구성해도 되는가? NAMUGA_ACS처럼 이중화/Failover가 필요한가?

**배경 (NAMUGA_ACS 분석)**:
- NAMUGA는 다중 프로세스(Control/Trans/Ei/Host, `Acs:Process:Type` 분기) + Control Server의
  CONTROL-HEARTBEAT 슈퍼바이저 + PRIMARY/SECONDARY 하드웨어 이중화 구조 — 관제 주도 반송
  시스템에서 "ACS 정지 = 물류 정지"이기 때문에 필요했던 설계.

**결정** (2026-07-15):
- HD_ACS 애플리케이션은 **단일 프로세스(모듈러 모놀리스)** 로 구성한다.
- **하드웨어 이중화/Failover는 초기 범위에서 제외**한다.
- OS 프로세스는 3개: HD_ACS 앱 + MQTT 브로커(Mosquitto) + PostgreSQL — 각각 OS 서비스
  (Windows 서비스/systemd) 등록 + 자동 재시작. 자체 슈퍼바이저는 만들지 않는다.

**근거**:
1. 온보드 실행 + Base 선릴리즈 + robot-is-truth[ADR-001/002] 구조에서 서버 다운은 로봇에게
   "통신 두절"과 동일 — 검사는 계속되고 재기동 후 state 재동기화로 복구된다. NAMUGA가 이중화로
   지키던 리스크가 구조적으로 부재.
2. 로봇 1~수 대·사용자 수 명 규모에서 프로세스 분리·이중화는 이득 없이 현장 운영 부담만 증가
   [ADR-003/006].
3. 브로커를 앱과 분리하면 앱 재기동 중에도 로봇 MQTT 연결·Last Will 상태가 유지된다.

**결과**:
- 모든 런타임 상태는 PostgreSQL에 저장(무상태 앱) — 기동 시간 수 초 유지가 품질 목표.
- 데이터 보호: pg_dump 스케줄 백업 + 서버 디스크 RAID1 권장 (이중화 대체 투자).
- 내부는 계층형 프로젝트 분리를 유지하여, 추후 fleet/상위 연동으로 가용성 요구 상승 시
  active-standby(PostgreSQL 복제 + VIP)로 구조 변경 없이 전환 가능하게 한다.

## ADR-012. 좌표 정의 프레임 — 벽면-로컬 2D 좌표계 검토 및 보류(현행 층 도면 프레임 유지) ✅

**질문**: 영역·검사작업(용접선)을 **벽면-로컬 2D 좌표계**로 정의하도록 바꿔야 하는가?
(제안: 벽면 등록으로 전체 면·좌표계 정의 → 벽면-로컬 2D로 영역·TASK 정의 → T_W_D로 AMR 이동 → T_A_B로 코봇 이동)

**검토 — 제안의 대부분은 현행 모델에서 이미 실현됨**:
- 영역(`min/max`)과 검사작업 seam(`[x,y,z]`)은 **이미 동일 프레임(해당 층 도면=floor-plan)** 에서 정의된다.
- **T_W_D → AMR 정차**: 이미 동작(`station=영역 중앙 → DrawingToMap → 맵 pose`, `AreaPlanningService`).
- **T_A_B → 코봇 이동**: 시스템 흐름상 맞으나 **HD_AMR의 책임**이다(ACS는 월드좌표 `seamStartW/EndW`까지만 제공, world→코봇 base 변환은 HD_AMR 티칭/온보드). 코드에 `T_A_B` 없음 — 경계 원칙(§6, ADR-001).

**진짜 새로운 것 = 벽면-로컬 2D 프레임** (§5에서 보류했던 항목):
- 실익: 벽 위 용접선 정의가 자연스러워짐(수직/챔퍼벽) + 3D 정확도. 현행은 top-down 프레임이라 수직벽 seam을 "≈일정 x,y + 변하는 z"로 표현.
- 전제/필요(현재 없음): ① 벽면별 **3D pose `T_world_wall`**(현 `ref.wall`은 레지스트리뿐) ② 변환 레이어 **2D→3D 확장**(현 T_W_D는 x,y,yaw만, z 통과) ③ 벽면-로컬 영역은 벽 위에 있으므로 **AMR 바닥 정차 투영**(벽 발치+standoff) 별도 필요 — 옛 `SeamSlicer`의 normal+standoff 방식으로 회귀.

**결정** (2026-08-06, 초안): 현행 층 도면 프레임 유지·벽면-로컬 보류. (아래 갱신으로 대체됨)

**갱신** (2026-08-06): **채택으로 전환 — "벽면-로컬 입력 레이어"를 단계적으로 도입**한다.
- 기반 결정: 벽면 pose는 **수동 입력**(원점+u/v축 또는 CAD 3점), 좌표는 **입력 시 도면 좌표로 변환**(generate/payload/T_W_D 코어 무변경). 벽면 pose = "벽면-로컬 2D(u,v) → 도면 3D[x,y,z]" 매핑.
- 도입 순서: ① 벽면 pose 기반(`ref.wall`에 origin/u_axis/v_axis + Core 3D 수학 `Vec3`/`WallPose` + 입력 API/UI) → ② AMR 바닥 정차 = 벽면 법선+standoff(`SeamSlicer` 로직 재사용, `FacingYawToward` 대체, 수직벽 정차 문제 해결) → ③ 영역·작업 (u,v) 입력·변환 → ④ generate/payload 통합 → ⑤ UI 전개도·문서.
- **Phase ① 완료** (2026-08-06): `Vec3`/`WallPose`(LocalToDrawing·Normal·HorizontalNormal·FromThreePoints) + 3D 수학 테스트, `ref.wall` pose 컬럼(비파괴 ADD COLUMN 마이그레이션), `POST/GET /api/walls` pose(3점) 입출력, UI 벽면 등록 pose 입력. 영역·작업·generate·payload는 무변경(② 이후).

**개정 (2026-08-07) — SPEC v3(`docs/SPEC_AREA_TASK_MANUAL.md`)로 구체화**: 벽면 pose를 **수동 입력**에서 **선창 파라메트릭 정의(팔각 단면)에서 자동 생성**으로 전환. §2 `ref.tank_geometry`(치수) → §3 10면 자동생성(`ref.wall` PK `(tank_id, wall_code)`, 프레임+내부향 법선+facing_yaw). Phase① `Vec3`/`WallPose`(=`To3D`) 재사용. **§2+§3(선창 3D 정의) 구현 완료** — 영역/작업(u,v §4)·정차 standoff(§5)·payload u,v(§6)·generate(§7)·전개도 UI(§9)는 후속. Phase① 수동 pose 입력 API/UI는 v3 자동생성으로 대체.
